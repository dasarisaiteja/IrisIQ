IRIS PROJECT – BACKEND DETAILED REQUIREMENTS
API + database + authentication + scan workflow + AI processing + report/PDF + role authorization
1. Objective
Build a secure backend that supports the public website, three roles (Admin/Student/Counsellor), student registration, assessment creation, separate left/right eye scans, AI/analysis processing, report data and PDF generation, counselling/follow-up, audit/error logging and role-based authorization.
2. Recommended Architecture
Authentication/Authorization service.
Student management module.
Assessment module.
Eye Scan module.
AI/Analysis integration module.
Report module.
PDF generation module.
Counsellor/assignment/counselling module.
Public contact/enquiry module if required.
Audit/logging module.
3. Roles & Permissions
Role
Permissions
Admin
Full management: users, students, assessments, scans/status, reports, counsellors, assignments, settings
Student
Own profile, own assessment, own scan status/flow, own report/PDF

10. Eye Scan Backend Rules
Validate assessment exists and user has access.
Accept only approved file/payload formats and enforce size limits.
Identify eye explicitly as LEFT or RIGHT; never infer from frontend labels alone.
Store scan metadata and secure file/object reference.
Prevent duplicate processing for the same scan request.
Mark scan Completed only after actual processing/validation succeeds.
Both eyes must belong to the same assessment.
Record timestamps, processing duration and safe error codes.
Do not expose raw sensitive files publicly.

Generate PDF from stored structured report data or an approved server-side template.
PDF must contain the same approved sections/values shown in the report UI.

Record report version and generated timestamp.
Return appropriate content type/download response or secure file URL according to deployment.

20. Suggested Relationships
One Student can have multiple Assessments over time.
One Assessment has exactly the required LEFT and RIGHT scan records.
One Assessment has one current/final analysis result set per report version.
One Assessment can have one or more report versions if regeneration/versioning is required.
One Assessment can be assigned to a Counsellor.
Counselling notes/follow-ups belong to an assessment/student context.

22. Security Requirements
Role-based authorization on every protected endpoint.
Validate ownership for Student APIs.
Counsellor can access only assigned/authorized students.
Use secure password hashing.
HTTPS in deployment.
Validate uploaded scan files.
Do not expose raw storage paths or secrets.
Sanitize logs and never log passwords/tokens.
Rate-limit authentication and sensitive endpoints where appropriate.
Use CORS restricted to approved frontend origins.

24. Logging & Audit
Log registration, login outcome (without password), scan submission, scan completion/failure, analysis start/end, report generation, counsellor assignment, report review and important admin actions.
Include user ID, role, assessment ID, timestamp and correlation/request ID where possible.
Keep technical stack traces server-side only.
25. Backend End-to-End Sequence
Admin/student creates registration.
Backend validates Student ID and creates/gets student record.
Backend creates Assessment ID.
Frontend uploads LEFT scan; backend validates/stores/processes it.
Frontend uploads RIGHT scan; backend validates/stores/processes it.
Backend confirms both scans completed.
Process endpoint creates AI/analysis job.
AI result is stored in analysis_results.
Report generation maps analysis data to official report structure.
Report metadata/PDF is stored securely.
Student/Admin/Counsellor retrieves only the report permitted by role.
26. Backend Acceptance Criteria
Three roles authenticate and are authorized correctly.
Registration creates a valid student and assessment.
Left/right scans are separately stored and tied to the same assessment.
Analysis cannot start before both scans complete.
Processing status can be queried.
Structured report API returns complete approved report data.
PDF can be generated/retrieved.
Counsellor assignment/notes/follow-up work.
Student can retrieve only own data.
Errors are consistent and safe.
Database constraints prevent duplicate/invalid relationships.
Postman collection/API documentation is supplied to frontend developer.

28. Important Official Report Rule
The exact report fields, scores, descriptions, charts and recommendations must be taken from the approved IRIS PDF/report template. Before production, backend and frontend developers must create a field-by-field mapping document so every PDF field has a source in the database/analysis response. No developer should invent assessment meaning or hard-code results.
